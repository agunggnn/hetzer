# ADR-0002: Landing the gate stack as stacked, per-gate pull requests

**Status:** Proposed
**Date:** 2026-10-13
**Deciders:** Maintainer (`agunggnn`). Nothing here authorizes a push or a pull request; both still need explicit approval.
**Related:** [ADR-0001](0001-authority-model-and-engine-boundary.md) (the gates this stack implements).

## Context

Gates G0, G1, G2 and G3 of ADR-0001 were built as local branches, one on top of the other, and nothing has been
pushed. `main` has not moved since the stack started (`c2e85cd`, PR #35), so every commit in the stack sits directly on
`main`'s tip.

Measured on 2026-10-13 from branch `feat/gate-g3-the-cut`:

| Segment | Commits | Files | Lines changed | Notes |
|---|---:|---:|---:|---|
| Independent one-commit fixes (upgrade checksum, broker limit event, git-hook lockfile, ESLint config, ADR-0001) | 5 | 18 | 2,065 | Also exist as five separate local branches; the stack carries cherry-picked copies with different hashes |
| G0 authority model and fail-closed signatures | 3 | 20 | 2,115 | |
| G1 sandbox defaults | 4 | 16 | 1,003 | |
| G2 contract, unified audit, id grammar, format version, vault schema v2 | 22 | 38 | 3,391 | Includes 4 evidence regenerations and 2 commits that mix concerns (see below) |
| G3 cut (module system, compose runner, stack orchestration) | 1 | 56 | 6,124 | 5,819 of the lines are deletions |
| **Whole stack** | **35** | **103** | **14,628** | Against `main` |

Observations that bear on the decision:

- The `/ultrareview` command refused the whole diff: its limits are 500 files and 8,000 changed lines, and the stack
  is 103 files and 14,628 lines. It suggested a closer base branch. Each segment above is under both limits.
- `main` merges by squash: its history reads `feat(sdk): add secure public application interface (#35)`. Squashing a
  stacked PR collapses the commits inside it.
- `docs/verification-evidence.json` is regenerated by `npm run verify` and is a tracked, generated file. It was
  regenerated in four separate commits in G2 alone. It conflicts with itself on any reorder or rebase and has to be
  regenerated at each PR tip.
- Two G2 commits mix concerns because another process swept uncommitted work into them: `8dbcf46` (guard
  deduplication plus lock, lock tests and the SEC-015 block) and `8f64b05` (the waiter marker, committed under a
  different message). History inside G2 is therefore not a clean per-concern record, and it was not rewritten.
- The vault schema v2 migration (`8bca6d0`) is the only destructive change in the stack: it drops tables in existing
  user vaults and removes the legacy JSON import and the `SHADOW_GRIMOIRE_KEY` fallback. It is a single commit with its
  own tests and doc edits, so it can be separated.
- G3 removes user-visible commands. ADR-0001 item 14 asks for a one-release deprecation pointer. It is in place, but
  two shipped documents still tell users to run the removed commands (see "Findings from the action items").
- Two PRs are open on the remote (#37 skill rules, #38 dependency updates). #38 shares no file with the stack. #37
  conflicts with every stack tip from G0 onward and adds a remote vault sync command (see the findings).
- Every tip was run through the full gate on 2026-10-13 and passed (see the findings). Before that only the earlier
  records existed (`VERIFY-SEC-007` to `VERIFY-SEC-015`), and a tip is only known to pass when it is run.
- Several agents edit one shared worktree. During G2 this swept work into the wrong commit twice and, once, switched the
  checked-out branch between two commits made from it.

## Decision

Land the stack as **stacked pull requests, one per gate, squash-merged in order**, with three refinements:

1. **Independent fixes first.** The five one-commit changes become their own PRs from their existing branches. After
   they merge, the stack is rebased on `main`; patch-equal commits drop out on rebase.
2. **G2 is two PRs.** G2a is everything except the vault schema v2 migration. G2b is the migration alone, so the only
   destructive change has its own review, its own evidence and its own revert point. G2a's evidence is generated at
   format version 1 and G2b flips it to 2.
3. **Gate and evidence are run at every PR tip**, from a clean detached worktree, with the key-free environment:
   `npm run check && npm test && npm run verify -- --no-write`, then `npm run verify` once in that worktree and the
   regenerated evidence file committed on its own.

PR order: independents, G0, G1, G2a, G2b, G3. Each PR targets the branch of the one before it until that one merges,
then is rebased onto `main` with `git rebase --onto main <previous tip>`.

This ADR does not decide the version bump or release notes for the removals in G3, whether G3 lands at all, or the
disclosure timing in ADR-0001 item 16.

## Options Considered

### Option A: One pull request with the whole stack

| Dimension | Assessment |
|---|---|
| Complexity | Low to open, high to review |
| Review | Cannot be reviewed by `/ultrareview` (14,628 lines against an 8,000 limit); a human reviewer sees a security change set and a 5,800-line deletion together |
| Rollback | All or nothing; reverting the destructive vault migration means reverting everything |
| Evidence | Regenerated once |

**Pros:** one merge, no retargeting, no intermediate states to verify.
**Cons:** the largest blast radius, the weakest review, and the only tool-assisted review path is closed.

### Option B: Stacked per-gate pull requests (chosen), with G2 split

| Dimension | Assessment |
|---|---|
| Complexity | Medium: sequential merges, rebase after each squash |
| Review | Every PR fits the review tool's limits (largest 56 files, 6.1k lines) and has one subject |
| Rollback | Per gate; the destructive migration reverts alone |
| Evidence | Regenerated at each tip, in its own commit |

**Pros:** reviewable pieces that match the ADR's own gates; the destructive change is isolated; each tip is
individually verified.
**Cons:** the squash-then-rebase dance on every step; the evidence file conflicts at each rebase; G2's inner history is
collapsed by the squash (the mixed commits above stop being visible, which is also the loss of a record).

### Option C: One pull request per commit

| Dimension | Assessment |
|---|---|
| Complexity | High: 35 PRs |
| Review | Many commits are follow-up fixes to the commit before them, so they are not coherent alone |
| Rollback | Fine-grained but not meaningful |
| Evidence | Several PRs would be nothing but regenerated evidence |

**Pros:** the finest bisect granularity.
**Cons:** no commit in the middle of a gate is a state anyone intended to ship, and the two mixed commits cannot be
reviewed as one concern.

### Option D: Merge the branches with merge commits, no squash

| Dimension | Assessment |
|---|---|
| Complexity | Low |
| Review | Same size problem as A unless it is also split into PRs |
| Rollback | Merge-commit revert per gate |
| Convention | Breaks the squash style `main` uses |

**Pros:** keeps all 35 commits.
**Cons:** puts the swept and mixed commits permanently on `main`, and does not solve the review size.

## Trade-off Analysis

The deciding forces are review size and the destructive migration. Option A fails the first outright. Option C pays
the process cost of B many times over for granularity nobody needs. Option D keeps history that is better kept in the
branch refs than on `main`. Between B and a plain per-gate split, the extra G2 split costs one more PR and one more
evidence regeneration, and buys a revert point for the only irreversible change, which is worth it.

The cost B carries is operational, not technical: each squash merge forces a rebase of the next branch, and the
generated evidence file conflicts every time. That is why regeneration is part of the decision rather than left to
whoever rebases.

## Consequences

- Reviews become possible per gate, including with `/ultrareview <base>` against the previous branch.
- The squash on G2 hides `8dbcf46` and `8f64b05`. The per-commit history stays in the local branch refs
  (`feat/gate-g2-contract` and the others); keep them until the last PR merges.
- Intermediate tips may fail the gate for reasons that were masked by later commits. That is a finding to fix in the
  PR, not a reason to skip the tip.
- Each rebase touches `docs/verification-evidence.json`; take the regenerated file, never a hand merge.
- Work on one PR from its own `git worktree`, so that no other agent's uncommitted changes can be swept into it.
- A change to the stack's content after a PR is open (a review fix) goes into that PR's branch and then up the stack
  by rebase, not into the tip.

### Vault schema v2 migration (`8bca6d0`)

- **V1. Credentials survive.** A version 1 vault with one credential, one target row and one finding row opened under
  the migration build: the credential decrypts, its grant signature verifies, the three tables are gone and the marker
  reads 2. The rows in the dropped tables are gone and no copy of the file is made first.
- **V2. An interrupted migration completes on the next open.** With two of the tables already dropped and the marker
  still at 1, the next open finishes and stamps 2. The missing transaction is therefore not a correctness problem;
  the concern recorded in the first version of this ADR does not hold.
- **V3. The migration can go unrecorded in the ledger.** Its audit event uses the fail-soft mirror. With a damaged
  last line in the ledger, and separately with a keyed ledger and a process that has no key, the tables were dropped
  and the marker stamped 2 while the ledger gained no `VAULT_MIGRATE_SCHEMA_V2` entry. Nothing retries it, because the
  marker is already 2. The migration also runs when the vault is opened locked.
- **V4. Concurrent opens are safe but noisy.** Four processes opening the same version 1 vault at once all succeeded and
  the ledger verified, with four migration entries.
- **V5. The format bump is what blocks going back.** The previous build refuses the migrated vault with
  `ERR_VAULT_FORMAT_UNSUPPORTED`. With the marker set back to 1 by hand, the same previous build opened it, decrypted
  the credential and verified its grant, because older builds re-create the missing tables. Dropping unused tables did
  not need a new format number; raising it makes the upgrade one-way. Whether that is wanted is a maintainer decision.
- **V6. The legacy JSON vault is ignored without a message.** A workspace with only `data/vault.json`: the previous
  build imports the entry, the migration build opens an empty vault, and `status()` no longer reports anything pending.
  Six call sites still pass `legacyFile`, which the constructor accepts and ignores.
- **V7. The retired key alias leaves the vault locked without a message.** With only `SHADOW_GRIMOIRE_KEY` set, in the
  process environment or in `.env`, the previous build resolves a key and the migration build resolves none. Nothing
  tells the user to rename the variable; what `init` does next was not tested. `docs/audit-batch-5.md` still lists the
  alias as a key source.
- **V8. `realm` is no longer checked.** A value outside the fixed set used to fall back to `frontier`; now any text is
  stored, cut at 60 characters, including a terminal escape sequence. The only reader outside the vault is the SDK
  metadata list, and `realm` takes part in no authorization decision.
- **V9. Two methods now accept data and keep none.** `recordAuditFinding` returns a new identifier and stores nothing
  (no caller is left in the repository); `upsertTarget` returns the id and stores nothing (four call sites in
  `cli/`, more in tests and the evidence script); `listTargets` is derived from credentials and no longer has host, port or source path.
- **V10. The migration itself has no test.** No test asserts that the tables are dropped, that the event is written or
  what happens to rows in the dropped tables; `VERIFY-SEC-015` checks the stamp only. Separately, ADR-0001 item 11
  still lists "dropping the SQLite audit table (item 12)" as open while item 12 is ticked and keeps that table.

Suggested before G2b opens, for the maintainer to accept or reject: a test for V1 and V2; a refusal or a warning for
V6 and V7 in place of silence; a decision on V5; and a mandatory, retried audit record for V3.

## Follow-up (2026-10-13)

The maintainer asked for the findings to be fixed and merged into the gate branches. The work was done in a separate
worktree on `fix/vault-v2-migration-safety` (from the G2 tip) and merged into G3; `feat/gate-g2-contract` was
fast-forwarded to it. Nothing was pushed.

- **V2, V4.** The drops, the marker and the SQLite audit row are one transaction. Four concurrent openers produce one
  migration row, and a failure inside the migration leaves the format 1 vault unchanged.
- **V3.** The ledger record is owed through a `vault_meta` marker and retried on every open until the ledger takes
  it. A process that opened the vault locked leaves it to one that has the key. It is written at least once, not
  exactly once: openers that overlap the writer can each write it.
- **V1.** The record carries the row count of each dropped table. The rows themselves are still not copied. No code in
  the repository before the migration wrote host, port or source-path values or any finding, so for a vault only
  Hetzer wrote, those tables held target ids that the credentials also carry. A vault another tool wrote into can
  lose more.
- **V6.** An unimported legacy JSON vault is reported once per file and process (`HETZER_LEGACY_VAULT_NOT_IMPORTED`)
  and in `status()`. It is still not imported.
- **V7.** Key lookup refuses with `ERR_MASTER_KEY_ALIAS_RETIRED` and a rename instruction when the retired alias is
  the key the previous build would have used. `hetzer init` refuses the same way: by reading its code, it would
  otherwise have written a new key into `.env` over a vault encrypted with the old one.
- **V10.** `cli/vault/vault-migration.test.mjs` has twelve tests. Each fix was removed in turn and at least one test
  failed for every removal (nine mutations). `VERIFY-SEC-015` gained three checks.
- **Not changed:** V5 (the format number), V8 (`realm` is free text) and V9 (`upsertTarget` and
  `recordAuditFinding` store nothing). They are listed as open under ADR-0001 item 12.
- **T1.** The writer was the MCP path, not a gate script: `resolveSecretRefsInPayload` and the `hetzer_vault_has`
  tool raised canary alerts without a root, so the incident log and the audit event went to the process directory, in
  the tests and in a real server started outside its instance directory. The callers now pass their root. A full gate
  run no longer changes `.hetzer/audit.log` or `data/hetzer-incidents.log` in the checkout.
- **C1.** The remaining names (`down`, `status`, `logs`, `modules`, `install`, `remove`, `module`) were run and
  behave the same; `check-update` prints the npm instruction and `version --check` prints the version only.
- **C2.** `README.md` and `docs/installation.md` no longer instruct users to run the removed commands or to reveal a
  gateway password that `init` does not generate. Left as it was: the requirements table still has a "Full Stack"
  row, and `init` still migrates only the four gateway variable names in `cli/vault/migrate-env.mjs`.

Gate on the merged tree (G3 with the fixes), key-free: `check` passed, 330 of 330 tests passed, `verify` VERIFIED. On
the fix branch alone (G2 with the fixes): 391 of 392 passed, 1 skipped, `verify` VERIFIED.

Consequence for the landing order: the fix commits sit on top of G2, so they belong to the G2b pull request together
with `8bca6d0`.
